## Performance

Three identical alternating runs: **480 initial-load samples** total; **60 per version/workload**, **600 scroll and 600 selection samples per table row**, plus **600 external commits**. Same host, Chromium process settings, 1280x900 viewport, 1000px grid, 400px viewport height, 120px columns, fictional rows, and alternating baseline/candidate order. Ten repetitions per run use explicit GC before each grid and ten use natural GC. Raw measurements and [full tables](evidence/v1.2.0/performance-tables.md) include p50, p95, min/max and sample counts; percentiles use nearest rank.

| Rows / columns | v1.1.0 adoption p50 / p95 | Candidate adoption p50 / p95 | Candidate range | n per version |
|---|---:|---:|---:|---:|
| 30,000 / 120 | 10.1 / 23.0 ms | 24.2 / 39.1 ms | 10.5–47.2 ms | 60 |
| 30,000 / 200 | 9.4 / 19.7 ms | 26.3 / 48.6 ms | 9.8–60.5 ms | 60 |
| 100,000 / 120 | 9.0 / 18.0 ms | 62.9 / 101.8 ms | 33.6–116.1 ms | 60 |
| 100,000 / 200 | 11.6 / 22.2 ms | 63.2 / 89.4 ms | 29.0–108.3 ms | 60 |

Adoption measures row assignment, connection and Lit update/DOM work. Fixture allocation and module/network loading are outside that timer. Two-animation-frame presentation waits are separately recorded; they are not compositor paint timings. Scroll samples include two animation frames, DOM work and scheduling, not just CPU time. No backend network time is measured or inferred.

At 100,000 rows, scroll p95 stays about **52–55 ms** across versions and selection p95 about **8–11 ms**. All wide-grid samples mount at most **260 cells**, independently of 120/200 logical columns and total row count; vertical/horizontal virtualization remains bounded. These observations do not establish a universal frame-time guarantee.

The core-only no-DOM/no-network control (`n=30` each) isolates the keyed cost: 100,000 rows with no `rowKey` has **0.4 / 0.8 ms** p50/p95; with `rowKey:'id'`, **31.2 / 69.3 ms**, range **27.7–71.5 ms**. At 30,000 keyed rows it is **9.0 / 15.4 ms**. Chromium CPU sampling puts `reconcile`, `rebuildKeys`, `refreshData`, `setData` and key reads at the top, with GC samples also present. The merged safety implementation scans for duplicate/valid keys and builds the displayed-key index on data transitions. v1.1.0 did not implement the new identity contract, so it does not pay this cost. The measurements demonstrate the cost; they do not justify removing duplicate-key protection or changing algorithms casually.

The earlier **311 ms** startup outlier did **not** recur: candidate maximum was **116.1 ms** across 240 candidate loads. Its original cause is not proven. The new repeated slowdown is broader than that isolated outlier and remains a release decision item. No improvement is claimed.

External pages of 20 rows, declared totals 352 / 30k / 100k / 1b, have respective p50/p95 **0.4/1.2**, **0.4/0.8**, **0.3/0.8**, **0.4/0.7 ms** (`n=150` each). One cold 352-total commit reached 20.9 ms; raw ranges are retained. Processing scales with loaded rows, not the declared total, in these fixtures.

Memory/GC observations: forced-GC sample snapshots range **4.4–15.9 MiB** baseline and **6.1–19.8 MiB** candidate; natural-GC snapshots range **2.5–59.5 MiB** and **2.4–80.3 MiB**, respectively (`n=120` per version/mode). Snapshots are taken after detached grids before the next collection and are not retained-leak measurements. The higher natural peak and GC variability warrant further soak testing. Production React's 50 browser-driven parent renders measured p50/p95 **49.6/60.8 ms**, range **29.8–121.1 ms**, including Playwright action scheduling; heap snapshots before/after GC were about 4.3/4.4 MiB. StrictMode's separate 50-render run is also recorded. Neither is a pure React render CPU benchmark or a proof of no leaks.

A separate **paired React 19.2.5 development-profiler benchmark** compares the actual v1.1.0 and candidate source adapters with identical local rows, two columns, changed `ariaLabel` on every parent update, stable versus replaced configuration, and a steady mounted Profiler (`50` updates per case, **400** total). At 30k rows both versions' update/presentation p95 is about **34–35 ms**. At 100k rows, stable-config p50/p95 is **33.3/34.3 ms** baseline versus **40.4/57.7 ms** candidate (candidate range 22.9–86.6 ms); fresh-config is **33.3/34.4 ms** versus **39.1/63.6 ms** (candidate range 22.6–83.5 ms). React Profiler render-duration p95 remains **0.2–0.3 ms** in those 100k cases; it excludes passive adapter effects and engine work. This separates small React reconciliation time from the slower post-render synchronization/frame pipeline. Full ranges and sample counts are in the performance tables. It supports the keyed synchronization investigation, not a claim of React rendering improvement.

**Blocking performance follow-up:** profile the initial configuration/data synchronization and key-index work, assess repeated scans, preserve invalid/duplicate identity safety, and propose a focused optimization with before/after evidence; alternatively approve an explicit keyed-local-data startup budget. Repeat these identical workloads before changing this gate to PASS. Small server pages are a mitigation for Property Management, not grounds to claim large local-data parity.

## Property Management risks and decision

No real tenant data was used. No Property Management files, credentials, infrastructure or deployed services were accessed or changed.

The application must own authorization and tenant/site scope at its BFF; a client `scopeKey` is not an authorization boundary. Keep monetary amounts as exact strings and compare them exactly on the server. UI sort/filter opt-outs do not disable imperative or server-query APIs. Replace external state immutably; cancel obsolete fetches and reject stale responses using both an account/site epoch and request identity. Changing scope invalidates the mounted grid's ID; remount or establish a greater controlled ID after the transition. Never retain detail/selection from an old scope.

Prefer small externally supplied pages for large tenant datasets. Stable keyed local loads of 100k rows have the measured startup regression. Unknown totals use -1 numeric sentinels; .NET total counts use the model's `int?` range. Keep npm wrappers and NuGet/bundled JS coordinated: the first `yc-grid` registration wins, and duplicate-registration guards cannot upgrade an old constructor already loaded on a page. Test cached-client upgrades separately before any deployment.

**Blocking:** measured large-local-row keyed startup regression, independent review of the focused fixes/workflow hardening, and final founder decision. No performance budget was supplied; accepting this regression requires an explicit decision rather than an inferred waiver.

**Proposed nonblockers requiring explicit acceptance:** the precise existing root TypeScript baseline, absent real screen-reader/Safari/touch/WASM coverage, the untested Angular-major support floor, local .NET SDK 10 versus CI SDK 8, and the unsupported local Node version for Angular 22. None permits advertising root TypeScript health, WCAG certification, or a fully tested framework/browser matrix.
